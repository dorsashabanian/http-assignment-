### سوال یک

- در HTTP/0.9 پروتکل بسیار ابتدایی بود، تنها متد GET را پشتیبانی می‌کرد، فاقد Header بود و عمدتاً برای انتقال محتوای HTML ساده استفاده می‌شد.
- در HTTP/1.0 Headerها اضافه شدند، از متدهای POST و HEAD و کدهای وضعیت پشتیبانی شد و امکان انتقال انواع مختلف محتوا با استفاده از MIME types فراهم شد. در این نسخه معمولاً برای هر درخواست یک اتصال TCP جدید برقرار می‌شد.
- در HTTP/1.1 اتصال پایدار معرفی شد، از Pipelining پشتیبانی شد و Header مربوط به Host برای پشتیبانی از هاست‌های مجازی و Chunked Transfer Encoding اضافه شد.
- در HTTP/2 قالب باینری جایگزین قالب متنی شد و Multiplexing برای ارسال همزمان چندین Stream روی یک اتصال TCP، فشرده‌سازی Headerها با HPACK و Server Push معرفی شدند.
- در HTTP/3 اجرا بر بستر QUIC که از UDP استفاده می‌کند انجام می‌شود، تأخیر برقراری اتصال با 0-RTT و 1-RTT کاهش می‌یابد و از Head-of-Line Blocking ناشی از TCP در سطح Streamهای مستقل جلوگیری می‌شود.


پروتکل TCP به صورت ذاتی دارای مشکل Head-of-Line Blocking در سطح اتصال است؛ به این معنا که اگر یک بسته TCP گم شود، بسته‌های بعدی تا دریافت مجدد آن بسته ممکن است منتظر بمانند. همچنین برقراری اتصال TCP و سپس TLS می‌تواند باعث افزایش تأخیر شود. پروتکل HTTP/3 به جای استفاده مستقیم از TCP، روی QUIC اجرا می‌شود و QUIC از UDP به عنوان بستر انتقال استفاده می‌کند. پروتکل QUIC با ایجاد Streamهای مستقل، مدیریت اتصال و رمزنگاری مبتنی بر TLS 1.3، امکان کاهش تأخیر و جلوگیری از وابستگی Streamهای مختلف به یکدیگر در برابر Packet Loss را فراهم می‌کند. دلیل اصلی انتخاب UDP این است که TCP در کرنل سیستم‌عامل و در میدل‌باکس‌هایی مانند فایروال و NAT پیاده‌سازی شده و تغییر دادن آن عملاً ممکن نیست؛ به همین دلیل QUIC روی UDP و در User Space ساخته شد تا بتواند آزادانه و سریع‌تر توسعه پیدا کند.


### سوال دو

**آ)**
ارتباط Stateless به ارتباطی گفته می‌شود که در آن هر درخواست مستقل از درخواست‌های قبلی پردازش می‌شود و سرور برای پردازش درخواست جدید به وضعیت درخواست‌های قبلی وابسته نیست. در مقابل، در ارتباط Stateful، وضعیت یا اطلاعات تعاملات قبلی حفظ می‌شود و می‌تواند در پردازش درخواست‌های بعدی مورد استفاده قرار گیرد.


**ب)**
پروتکل HTTP ذاتاً یک پروتکل Stateless است. برای ایجاد امکان حفظ وضعیت کاربر، مانند احراز هویت، نگه‌داری سبد خرید یا شخصی‌سازی، از روش‌هایی مانند Cookies، Session Management و Token استفاده می‌شود تا اطلاعات لازم برای شناسایی و حفظ وضعیت کاربر در درخواست‌های بعدی در دسترس باشد.


### سوال سه

**آ) :**
ماهیت معمول HTTP در مدل Request/Response به این صورت است که Client آغازکننده درخواست است و Server در پاسخ به آن داده ارسال می‌کند. بنابراین Server بدون وجود یک درخواست یا اتصال از سمت Client، در مدل سنتی HTTP امکان ارسال خودجوش و فوری اطلاعات به Client را ندارد. در کاربردهایی مانند Alerting و به‌روزرسانی‌های لحظه‌ای، این محدودیت باعث می‌شود Client مجبور به استفاده از روش‌هایی مانند Polling شود که می‌تواند باعث افزایش تأخیر و مصرف منابع شود.


**ب) :**
روش Long Polling (نظرسنجی طولانی): در این روش Client یک درخواست به Server ارسال می‌کند و Server درخواست را تا زمانی که داده جدیدی برای ارسال وجود داشته باشد باز نگه می‌دارد. پس از آماده شدن داده، Server پاسخ را ارسال می‌کند و Client بلافاصله درخواست جدیدی ایجاد می‌کند. این روش نسبت به Polling معمولی تأخیر و تعداد درخواست‌ها را کاهش می‌دهد، اما همچنان به چرخه Request/Response وابسته است و می‌تواند منابع Server را درگیر کند.

روش WebSocket (وب‌سوکت): وب‌سوکت یک پروتکل ارتباطی برای ایجاد یک اتصال دائمی و دوطرفه (Full-duplex) است. پس از Handshake اولیه، ارتباطی پایدار برقرار می‌شود و Client و Server می‌توانند در هر زمان و به صورت مستقل از یکدیگر داده ارسال کنند. این روش برای کاربردهایی مانند Chat، بازی‌های آنلاین و سیستم‌های Real-time مناسب است.

روش Server-Sent Events یا SSE (سرور سنت ایونتس): در این روش Client یک اتصال HTTP را برقرار و باز نگه می‌دارد و Server می‌تواند از طریق همان اتصال، جریانی از رویدادها و داده‌ها را به صورت یک‌طرفه برای Client ارسال کند. این روش برای کاربردهایی مانند Alerting، اعلان‌ها و به‌روزرسانی‌های زنده مناسب است. برخلاف WebSocket، ارتباط SSE برای ارسال داده از Server به Client طراحی شده و یک کانال دوطرفه کامل ایجاد نمی‌کند.



### سوال چهار

`ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1`
- **Scheme:** `ss`
- **User Information:** `asghar:1234!!`
  - **Username:** `asghar`
  - **Password:** `1234!!`
- **Host:** `ss.myproxy.com`
- **Port:** `1234`
- **Fragment:** `shadowSocks1`

این URL دارای Path و Query نیست.


### سوال پنج

#### ۱. دیتابیس وبسایت شما مشکل پیدا کرده و درخواست‌های لاگین انجام نمی‌شوند.

- **کد پیشنهادی: `503 Service Unavailable`**
- **دلیل:** سرور به دلیل در دسترس نبودن یک سرویس وابسته، یعنی Database، در حال حاضر قادر به پردازش درخواست‌های Login نیست. این وضعیت می‌تواند موقتی باشد؛ بنابراین `503` انتخاب مناسبی است.

#### ۲. نام‌کاربری‌ای که کاربر وارد کرده داخل سایت وجود ندارد و Login موفقیت‌آمیز نبود.

- **کد پیشنهادی: `401 Unauthorized`**
- **دلیل:** کاربر نتوانسته با اطلاعات احراز هویت ارائه‌شده هویت خود را اثبات کند؛ بنابراین `401` برای نشان دادن شکست احراز هویت مناسب است. پیام خطا برای «نام‌کاربری وجود ندارد» و «رمز عبور اشتباه است» باید یکسان باشد تا کسی نتواند با آزمون و خطا نام‌کاربری‌های موجود را حدس بزند (User Enumeration).

#### ۳. وبسایت به دامنه دیگری منتقل شده است.

- **کد پیشنهادی: `301 Moved Permanently`**
- **دلیل:** انتقال دائمی است و `301` نشان می‌دهد که منبع به آدرس دیگری منتقل شده و Client می‌تواند از آدرس جدید استفاده کند. گزینه‌ی دیگر `308 Permanent Redirect` است که متد درخواست (مثلاً POST) را هنگام Redirect حفظ می‌کند.

#### ۴. تعداد درخواست‌هایی که از طرف این کاربر ارسال شده از نرخ مجاز بیشتر است.

- **کد پیشنهادی: `429 Too Many Requests`**
- **دلیل:** این Status Code برای زمانی استفاده می‌شود که Client در یک بازه زمانی تعداد درخواست بیشتری از حد مجاز ارسال کرده باشد و به اصطلاح Rate Limit را نقض کرده باشد.

#### ۵. درخواست تمدید توکن (JWT) موفقیت‌آمیز بوده و توکن تمدیدشده داخل Header بازگردانده شده است.

- **کد پیشنهادی: `200 OK`**
- **دلیل:** درخواست با موفقیت پردازش شده و نتیجه، یعنی توکن جدید، در Response بازگردانده شده است.

#### ۶. کاربر از رنج IP ممنوعه برای دسترسی به سرویس است (تحریم شده).

- **کد پیشنهادی: `451 Unavailable For Legal Reasons`**
- **دلیل:** در صورتی که دلیل مسدودسازی، محدودیت یا الزام قانونی باشد، `451` به طور مشخص برای نمایش عدم دسترسی به منبع به دلایل قانونی تعریف شده است. اگر مسدودسازی صرفاً یک سیاست امنیتی یا دسترسی باشد و دلیل قانونی مطرح نباشد، `403 Forbidden` نیز می‌تواند مناسب باشد.


### سوال شش

#### ۱. استفاده از سرورهای داخلی دانشگاه برای دریافت پکیج‌ها از Package Manager (مانند apt برای Ubuntu)

- **نوع Proxy: `Forward Proxy` با قابلیت `Caching`**
- **توضیح:** Clientهای داخل دانشگاه درخواست‌های خود را به Proxy ارسال می‌کنند و Proxy از طرف آن‌ها به سرورهای Package Repository متصل می‌شود. در صورت فعال بودن Cache، پکیج‌های دریافت‌شده می‌توانند برای درخواست‌های بعدی ذخیره شوند تا مصرف پهنای باند و زمان دریافت کاهش پیدا کند. بنابراین از دید Client، این Proxy یک Forward Proxy است.

#### ۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست‌ها

- **نوع Proxy: `Reverse Proxy`**
- **توضیح:** Reverse Proxy در سمت Server قرار می‌گیرد و با بررسی IP یا موقعیت جغرافیایی Client، درخواست را به Server مناسب هدایت می‌کند؛ برای مثال کاربران یک منطقه می‌توانند به Server همان منطقه هدایت شوند. این کار می‌تواند باعث کاهش تأخیر و بهبود عملکرد شود.

#### ۳. اضافه کردن قابلیت احراز هویت برای یک سرویس بسیار قدیمی

- **نوع Proxy: `Reverse Proxy` یا `API Gateway`**
- **توضیح:** می‌توان سرویس قدیمی را پشت یک Reverse Proxy قرار داد تا Proxy قبل از ارسال درخواست به سرویس، عملیات Authentication و کنترل دسترسی را انجام دهد. به این ترتیب می‌توان بدون تغییر دادن خود سرویس قدیمی، قابلیت احراز هویت را به آن اضافه کرد. در معماری‌های APIمحور، همین نقش می‌تواند توسط API Gateway انجام شود.
